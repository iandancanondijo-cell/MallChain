## 1. Admin Login + 2FA TOTP Setup

### 1.1 Prerequisites

- Superadmin account provisioned in the `superadmins` table with `is_active = true`
- Valid email address registered to the superadmin account
- Authenticator app installed (Authy, Google Authenticator, 1Password, or similar TOTP-compatible app
- Backup storage medium (password manager or encrypted vault for backup codes

### 1.2 Initial Login Flow

1. Navigate to `https://admin.mallchain.io/login`
2. Enter registered email address in the email field
3. Enter the superadmin password (minimum 16 characters, rotated every 90 days per policy
4. Click "Sign In" button
5. On first successful login, the system will redirect to the 2FA enrollment wizard automatically
6. If 2FA is already enrolled, proceed to Section 1.4

### 1.3 TOTP Enrollment - Scan QR Code

1. The enrollment wizard displays a 6-digit alphanumeric setup key below the QR code
2. Open your authenticator app
3. Select "Add Account" or "+" icon
4. Choose "Scan QR Code" option
5. Point device camera at the QR code displayed on the admin panel
6. Verify the account name shows "Mallchain Superadmin: <your-email@domain.com>"
7. Verify the issuer field shows "Mallchain" in the authenticator app
8. Tap "Save" or "Done" in the authenticator app to store the seed

### 1.4 TOTP Verification

1. Return to the Mallchain admin panel enrollment screen
2. Enter the 6-digit TOTP code generated by your authenticator app into the "Verification Code" field
3. Click "Verify and Activate" button
4. System validates the TOTP code against the server-side clock (±1 step tolerance)
5. Upon successful validation, the system proceeds to display the backup codes screen
6. If validation fails:
   - Check device clock synchronization (NTP recommended)
   - Wait 30 seconds for the next code rotation
   - Re-enter the fresh 6-digit code
   - If 3 consecutive failures, account locks for 15 minutes; contact another superadmin for unlock

### 1.5 Backup Codes Storage

1. The system generates 10 one-time-use 8-character alphanumeric backup codes
2. **CRITICAL**: Copy ALL 10 codes to a secure location immediately. These codes are hashed server-side and cannot be retrieved after this screen
3. Recommended storage options:
   - Print to physical paper and store in a safe
   - Save to encrypted password manager entry marked "Mallchain Superadmin Backup Codes"
   - Save to hardware-encrypted USB drive stored offsite
4. **DO NOT**:
   - Store backup codes in the same password vault (you use for daily password storage
   - Email backup codes to yourself or anyone
   - Screenshot backup codes to unencrypted cloud storage
4. Tick the checkbox "I have securely stored all backup codes"
5. Click "Confirm and Complete Enrollment"
6. System redirects to the admin dashboard

### 1.6 Enforce 2FA Policy for All Superadmins

1. Navigate to Admin Panel → System Settings → Security Policies
2. Locate the "Two-Factor Authentication Enforcement" section
3. Set "Require TOTP for All Superadmin Logins" toggle to ENABLED
4. Set "Grace Period for Enrollment" to 0 hours (immediate enforcement)
5. Set "Remember Device" duration to 0 hours (prompt for TOTP on every login)
6. Under "Allowed 2FA Methods", ensure only "TOTP (Authenticator App)" is checked
7. Ensure SMS and email-based 2FA methods are **UNCHECKED** (insecure per policy MALL-SEC-007)
8. Click "Save Policy Changes"
9. Enter current superadmin password to confirm policy change
10. Enter TOTP code for second-factor confirmation
11. System logs the policy change to the superadmin audit log with timestamp, admin ID, and before/after policy state

## 2. KYC Review Queue

### 2.1 Accessing the KYC Review Queue

1. Log into the admin panel with valid credentials + TOTP
2. From the left navigation sidebar, select "Compliance" → "KYC Review Queue"
3. The queue displays all submissions with `status = 'PENDING_REVIEW'` sorted by submission timestamp (oldest first, per FCFS policy
4. Queue filters available:
   - Filter by KYC level: L1 (Basic), L2 (Full), L3 (Institutional)
   - Filter by country code (ISO 3166-1 alpha-2)
   - Filter by submission date range
   - Filter by assigned reviewer
5. Click a row to open the KYC review detail pane

### 2.2 Understanding maskIdNumber Behavior

- By default, all government ID numbers are masked in the list view and initial detail view
- The `maskIdNumber` function applies the following masking rules:
  - US SSN: `XXX-XX-1234` (last 4 digits visible)
  - Passport numbers: first 2 and last 2 characters visible, middle masked
  - National ID cards: varies by jurisdiction, minimum 60% of characters masked
- The full ID number is **never** cached in browser localStorage, sessionStorage, or browser memory longer than the lifetime of the sensitive PII modal
- Full ID numbers are never logged to application logs, audit logs, or error traces (replaced with `[REDACTED]` token)

### 2.3 Viewing Full ID via Sensitive PII Modal

**WARNING**: Re-enter your admin password each time you open the sensitive PII modal. This is a mandatory security control per MALL-SEC-014. Failure to re-authenticate on every PII exposure event is an audit finding.

1. In the KYC review detail pane, locate the "ID Verification" card
2. Click the "Show Full ID Number" button (red shield icon)
3. The sensitive PII modal appears with the following security banner warning:
   > SENSITIVE PII EXPOSURE WARNING: This action is logged. Your session is recorded to the superadmin audit log including timestamp, admin ID, user ID being reviewed, and IP address.
4. In the modal footer, enter your **current superadmin account password (not the user's password)
5. Click "Confirm Identity and Unmask ID Number"
6. System validates password against bcrypt hash (cost factor 12)
7. Upon success, the full ID number is decrypted using the envelope encryption key (AES-256-GCM via AWS KMS / equivalent HSM-backed)
8. Full ID number displays for a maximum of 60 seconds; after 60 seconds the modal auto-closes and the in-memory plaintext is zeroed
9. If you need more time, click "Extend Viewing" (requires password re-entry required again)
10. When finished, click "Close and Zero Memory" button; system performs explicit memory zeroization of plaintext ID number
11. **Audit log entry created with fields: `event_type='PII_UNMASK', admin_user_id='<admin-id>', target_user_id='<user-id>', ip_address='<x.x.x.x>', session_id='<sid>', kyc_submission_id='<kyc-id>', timestamp

### 2.4 Approve KYC Submission

1. Review all required document authenticity, document photos (front/back), and biometric match score (>0.85 threshold configured in `/admin/settings/compliance
2. Verify the following fields:
   - Full name matches government ID exactly
   - Date of birth within ±1 day of ID document
   - Address proof document date < 90 days old
   - Selfie photo matches ID photo (liveness detection score > PASS threshold
   - AML / sanctions screening: no matches on OFAC, UN, EU sanctions lists
   - PEP (Politically Exposed Person) check: no Level 1/2/3 matches
3. If all checks pass:
   a. Click "Approve" button (green checkmark icon)
   b. In the confirmation modal, enter mandatory approval notes (minimum 20 characters required
   c. Notes template: "Reviewed on YYYY-MM-DD by <initials>: All documents verified. Liveness score: X.XX. AML/PEP clear."
   d. Click "Confirm Approval"
4. System transitions KYC status from `PENDING_REVIEW` → `APPROVED`
5. User receives in-app notification + email confirmation
6. Badge eligibility engine evaluates for any automatic badge grants (bronze/silver on KYC tier thresholds
7. Audit log entry: `event_type='KYC_APPROVE'

### 2.5 Reject KYC Submission

1. Identify the specific failure reason(s):
   - Document illegible
   - Document expired
   - Document does not match selfie
   - Name mismatch across documents
   - Address proof insufficient
   - AML/sanctions match
   - PEP match
   - Suspected fraudulent submission
2. Click "Reject" button (red X icon)
3. In the rejection modal:
   a. Select rejection category from dropdown (predefined list)
   b. Enter mandatory rejection notes (minimum 30 characters
   c. Tick checkboxes for all specific rejection reasons (must tick at least one)
   d. If fraud is suspected, tick "Flag for fraud review" (escalates to compliance lead
4. Click "Confirm Rejection"
5. System transitions KYC status from `PENDING_REVIEW` → `REJECTED`
6. User receives in-app notification + email with generic rejection reason (specific internal notes are NOT shared with user
7. User may re-submit KYC after 24-hour cooldown
8. Audit log entry: `event_type='KYC_REJECT'

## 3. Maintenance Mode Emergency Halt

Reference: See `docs/runbooks/maintenance-mode-emergency-halt.md` for full curl payload examples.

### 3.1 Pause Per-Module (Granular Control)

Use per-module pause when only specific subsystems are affected. This allows partial platform

```bash
# Pause individual modules (example payload)
curl -X POST https://admin.mallchain.io/api/v1/maintenance/pause \
  -H "Authorization: Bearer $SUPERADMIN_JWT" \
  -H "X-Admin-2FA: $TOTP_NOW" \
  -H "Content-Type: application/json" \
  -d '{
    "modules": ["payment-gateway", "withdrawal-engine"],
    "reason": "Payment processor API degradation incident #INC-2026-0827-001",
    "halted_by": "admin-super-01",
    "duration_minutes": 30
  }'
```

Affected modules enter `PAUSED` state:
- `payment-gateway`: Blocks all new payment submissions; queues internally
- `withdrawal-engine`: Stops processing withdrawal requests; user sees "System Maintenance"
- `kyc-engine`: Pauses KYC document uploads
- `badge-engine`: Pauses badge purchases and auto-issuance
- `liquidity-module`: Pauses DEX swaps and liquidity add/remove
- `treasury-module`: Pauses all treasury operations (NOT the MLCNS conversion
- `marketplace`: Pauses new listing creation and order matching

### 3.2 Global Halt (Full Platform Stop)

**CRITICAL: Global halt stops all user-facing and internal operations. Only use when there is an active security incident, data corruption risk, or cascading failure detected.

```bash
# EMERGENCY GLOBAL HALT
curl -X POST https://admin.mallchain.io/api/v1/maintenance/global-halt \
  -H "Authorization: Bearer $SUPERADMIN_JWT" \
  -H "X-Admin-2FA: $TOTP_NOW" \
  -H "X-Emergency-Auth: $EMERGENCY_HMAC_SIGNATURE" \
  -H "Content-Type: application/json" \
  -d '{
    "reason": "Active exploit in the wild — CVE-2026-XXXX being actively exploited",
    "halted_by": "admin-super-01",
    "requires_2_signatures": true,
    "emergency_incident_id": "INC-2026-0827-001"
  }'
```

Global halt behavior:
- All modules transition to `HALTED` state within 500ms of receipt
- All WebSocket connections drain and close with code 4001 "SYSTEM_HALTED"
- All API endpoints return HTTP 503 with `Retry-After: 300
- Blockchain tx/message queues stop processing; messages retained
- On-chain operations are NOT HALTED; on the blockchain network layer continues
- User-facing UI shows branded "Emergency Maintenance" landing page
- SRE and DevOps on-call paged automatically via PagerDuty webhook

### 3.3 Status Check

```bash
# Check maintenance mode status for all modules
curl -X GET https://admin.mallchain.io/api/v1/maintenance/status \
  -H "Authorization: Bearer $SUPERADMIN_JWT"
```

Response includes per-module state, halt reason, halted_by timestamp, halt duration elapsed, and estimated_resume_time if set.

### 3.4 Resume Operations

Resume requires the **two** superadmin approvals.

```bash
curl -X POST https://admin.mallchain.io/api/v1/maintenance/resume \
  -H "Authorization: Bearer $SUPERADMIN_JWT" \
  -H "X-Admin-2FA: $TOTP_NOW" \
  -H "Content-Type: application/json" \
  -d '{
    "resumed_by": "admin-super-01",
    "second_signature_admin_id": "admin-super-02",
    "incident_closed": true,
    "post_resume_checklist_run_id": "PR-2026-0827-001"
  }'
```

### 3.5 After-Resume Checklist

Execute these steps after resume succeeds in **ORDERED** order.

1. **Replay Dead Letter Queues first (see Section 7)
   - Replay `convert-liquidity-dlq`
   - Replay `tx-dead-letter`
   - Replay `payment-callback-dlq`
2. **Run Reconciliation Jobs
   - Treasury reconciliation: `npm run reconcile:treasury -- --start=<halt-timestamp --end=<resume-timestamp>`
   - Wallet balance reconciliation: `npm run reconcile:wallets`
   - Badge issuance reconciliation: `npm run reconcile:badges`
   - Payment ledger reconciliation: `npm run reconcile:payments`
3. **Verify DLQ backlog drained to zero messages
4. **Verify blockchain sync lag < 3 blocks behind tip
5. **Check Redis queues depth < 100 pending
6. **Verify API p99 latency < 500ms
7. **Check error rates < 0.1% across all endpoints
8. **Send "All Clear" notification to #incident-announce Slack channel
9. **Close incident ticket with post-mortem link

## 6. Treasury Rebalance

### 6.1 Purpose

Treasury rebalance converts between MLCNS and USD in the vault reserves to maintain target 1:1.5 collateralization ratio between the liquidity pools within 2% band. Rebalance is required when the collateralization ratio drifts.

### 6.2 Access Treasury Panel

1. Navigate to Admin Panel → Treasury → Rebalance
2. The dashboard shows:
   - Current MLCNS vault balance
   - Current USD vault balance (via bank wire / stablecoin equivalents)
   - Current collateralization ratio (target 150%, upper 152%, lower 148%
   - Deviation from target band
   - Recommended conversion direction

### 6.3 Convert MLCNS → USD

When ratio > 152% (excess MLCNS reserves):

1. Locate the "Convert MLCNS → USD card
2. Enter the amount in MLCNS to sell from the recommended amount (read-only by default, edit only if CFO approval override ticket attached)
3. Reference the approved ticket field required (TREAS-XXXX
4. Click "Prepare Conversion Proposal"
5. Review the unsigned conversion transaction
6. **DO NOT SIGN HERE** — signing requires the actual on-chain multisig via air-gapped signing ceremony per policy MALL-TRES-003
7. Click "Export Unsigned Payload as JSON"
8. Save to USB drive for air-gapped transfer to the cold wallet signers (3-of-5 multisig quorum required)
9. After signed payload obtained from the quorum, return here
10. Click "Import Signed Payload and Broadcast
11. Upload signed JSON
12. Click "Verify Signatures (3 valid signatures confirmed from the treasury multisig set
13. Upon valid, broadcast to chain
14. Upon confirmation, reconcile

### 6.4 Convert USD → MLCNS

When ratio < 148% (insufficient MLCNS reserves):

1. Locate the "Convert USD → MLCNS card
2. Enter amount (recommended amount, read-only
3. Attach TREAS-XXXX reference ticket
4. Click "Prepare Mint Proposal"
5. **DO NOT SIGN HERE
6. Export unsigned payload
7. Transfer to air-gapped quorum signers
8. After signed, import and broadcast signed payload
9. Verify signatures and broadcast to chain mint

### 6.5 Reconciliation Pending Manual UI

After each conversion, both directions:
- Links to: See `docs/runbooks/treasury-reconciliation.md (manual reconciliation pending automated UI completion)
- Run: `npm run reconcile:treasury-ledger -- --tx=<txhash>`
- Verify the `treasury_ledger` entries match the bank statement / stablecoin transfer confirmation
- Both entries in `TreasuryLedger` collection match
- Audit log: `event_type='TREASURY_REBALANCE', direction, amount, both signature refs

## 7. Force DLQ Replay

Reference: See `docs/runbooks/dead-letter-outbox.md` for full CLI details.

### 7.1 DLQ Queues Available

| Queue Name | Purpose | Typical Contents |
|------------|---------|----------------|
| `convert-liquidity-dlq` | DEX liquidity conversion failures | Failed liquidity add/remove during slippage tolerance exceeded, RPC timeouts |
| `tx-dead-letter` | General blockchain transaction failures | Nonce collisions, out-of-gas, mempool evictions, chain reorgs |
| `payment-callback-dlq` | Payment gateway callback failures | Webhook delivery failures to payment providers (Stripe/Adyen failures, 5xx on provider callbacks |

### 7.2 CLI Replay Commands

```bash
# 1. Inspect DLQ counts
redis-cli -h redis.mallchain.local -p 6379 -a $REDIS_AUTH_KEY \
  LLEN convert-liquidity-dlq \
  LLEN tx-dead-letter \
  LLEN payment-callback-dlq
```

```bash
# 2. Peek first 10 messages from tx-dead-letter without removing
node backend/src/queue/dlq-inspect.js --queue tx-dead-letter --peek 10
```

```bash
# 3. Replay convert-liquidity-dlq (10 messages per second throttle
node backend/src/queue/dlq-replay.js \
  --queue convert-liquidity-dlq \
  --rate 10 \
  --auth $SUPERADMIN_API_KEY \
  --dry-run false
```

```bash
# 4. Replay tx-dead-letter ALL messages
BACKFILL=true node backend/src/queue/dlq-replay.js \
  --queue tx-dead-letter \
  --rate 50 \
  --stop-on-error false \
  --log-every 100
```

```bash
# 5. Replay payment-callback-dlq with idempotency key validation
node backend/src/queue/dlq-replay.js \
  --queue payment-callback-dlq \
  --validate-idempotency true \
  --rate 5
```

### 7.3 Post-Replay Verification

After each DLQ replay run completes:
1. Verify `LLEN <queue> = 0 for each replayed queue
2. Check `replayed_success` / replayed_failed` counters
3. Review remaining messages are not zero, inspect for poison-pill messages
4. Any poison pill: move to `poison-<queue>` list with `dlq-poison.js`
5. Notify affected users of order reconciliation

## 8. Superadmin Audit Log Rotation 90 Days Encrypted

### 8.1 Policy

- Superadmin audit logs retained for 90 days in hot storage (MongoDB `superadmin_audit_logs collection
- After 90 days, automatically rotated to cold storage (encrypted S3 / GCS bucket with object lock, 7-year retention Legal hold)
- Rotation runs daily at 02:00 UTC via cron job in the operator server

### 8.2 Manual Rotation Trigger

Trigger ahead of schedule if needed:

```bash
# Trigger manual audit log rotation
curl -X POST https://admin.mallchain.io/api/v1/audit/rotate \
  -H "Authorization: Bearer $SUPERADMIN_JWT" \
  -H "X-Admin-2FA: $TOTP_NOW" \
  -H "Content-Type: application/json" \
  -d '{
    "rotate_before": "2026-06-01T00:00:00Z",
    "rotation_reason": "Sensitive investigation export for legal hold request LHLD-789"
  }'
```

### 8.3 Encryption Specifications

- At-rest encryption: AES-256-GCM, keys: HKDF-derived keys
- Data encryption keys (DEK) rotated every 90 days
- Key encryption keys (KEK) stored in AWS KMS / HSM-backed FIPS 140-2 Level 3
- Object lock enabled on cold storage bucket with COMPLIANCE mode (cannot be overwritten/deleted for 7 years
- Export access: only Legal + Compliance team role, require 2-person integrity for access to exports

### 8.4 Verification of Rotation Completion

1. Navigate to Admin Panel → System → Audit Log Rotation History
2. Confirm today's rotation entry with:
   - status: SUCCESS
   - records_rotated count > 0
   - cold_storage_uri: `s3://mallchain-audit-logs-cold/...`
   - sha256_manifest_hash matches local verification
3. Verify hot storage no longer contains records older than rotation date
4. Export manifest signed by two superadmins
